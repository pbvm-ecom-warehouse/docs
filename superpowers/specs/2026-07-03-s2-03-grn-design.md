# S2-03: UC-02 GRN (Goods Receipt Note) — Design

**Sprint:** 2 · **Size:** L · **Depends-on:** S1-04 (stock schema/transaction helper), S2-02 (purchase-order)

## Bối cảnh

Good Receive Note (GRN) là chứng từ ghi nhận **hàng thực nhận** theo một Purchase Order (PO). Khi GRN được RECEIVER xác nhận (`CONFIRMED`), hệ thống phải:

1. Cộng tồn **2 lớp** (`stock_balances` + `inventory_stocks`) trong 1 transaction, ghi `StockMovement` (sổ cái append-only).
2. Cộng dồn số đã nhận vào PO, cập nhật trạng thái PO (`PARTIALLY_RECEIVED`/`COMPLETED`).
3. Phát event `stock.changed(+)` cho Ecommerce sync `availableQty`.

Tham chiếu: [warehouse/use-cases.md UC-02](../../warehouse/use-cases.md), [warehouse/workflow.md WF-01](../../warehouse/workflow.md), [db/02-hang-hoa-va-ton-kho.md](../../db/02-hang-hoa-va-ton-kho.md), [db/03-nhap-kho.md](../../db/03-nhap-kho.md), [planning/issues/S2-03-grn.md](../../planning/issues/S2-03-grn.md).

### ⚠️ Sai lệch giữa doc issue gốc và code thực tế

`docs/planning/issues/S2-03-grn.md` nhắc tới helper `applyStockChange` và `StockMovement` type `RECEIPT`. **Cả hai không tồn tại trong code.** Thực tế đã có từ S1-04:

- `StockTransactionHelper.withStockTransaction(fn)` — wrapper `session.withTransaction`, cần replica set.
- `StockRepository` với các method rời: `upsertBalance`, `upsertInventory`, `findActiveLotByNumber`, `createLot`, `insertMovement`, `findSkuById`.
- `MovementType` enum có giá trị `RECEIVE` (không phải `RECEIPT`).

→ GRN service tự orchestrate 3 lời gọi (`upsertBalance` + `upsertInventory` + `insertMovement`) bên trong `withStockTransaction`, dùng `MovementType.RECEIVE`, `refType: 'grn'`. Theo code, không theo doc issue.

## Phạm vi

### Trong phạm vi

- Schema `GoodsReceiptNote` (+ sub-doc `GoodsReceiptNoteItem`) tham chiếu PO.
- API tạo GRN (`DRAFT`), confirm (`DRAFT → CONFIRMED`, cộng tồn 2 lớp + cập nhật PO), approve (`CONFIRMED → APPROVED`, thuần audit).
- API list/detail GRN.
- Validate: item phải thuộc PO; perishable thiếu lot/expiry → 400; vượt `expectedQty` còn lại của PO → chặn toàn bộ confirm.
- Quy đổi đơn vị phụ → đơn vị cơ sở khi cộng tồn (`baseQty = qty × factor`).
- Xác định shelf staging của kho (thêm `warehouseId` denormalized vào `Shelf`).
- `PurchaseOrder` thêm `receivedQty` tích lũy theo item + method cộng dồn/cập nhật status, dùng chung transaction session với GRN.
- Phát `stock.changed(+)` sau khi transaction commit (tái dùng `StockService.publishAvailableForItem`).

### Ngoài phạm vi (để sprint sau)

- API sửa/xóa item khi GRN còn `DRAFT` (sai thì tạo GRN mới).
- Endpoint "scan" barcode riêng — FE tự quét, gửi thẳng `itemId`/`sku` lên API tạo GRN; BE chỉ validate dữ liệu.
- Cho phép item ngoài PO (append thêm dòng hàng không có trong PO gốc).
- Put-away (UC-03) — GRN chỉ đưa hàng vào shelf staging, chuyển từ staging sang shelf thật là việc của S2-04.
- Xử lý chênh lệch với NCC (chỉ chặn vượt qty, không có luồng nghiệp vụ khiếu nại NCC).

## Trạng thái GRN

| Status | Mô tả | Chuyển từ |
|---|---|---|
| `DRAFT` | Đang nhập liệu, chưa cộng tồn | (khởi tạo) |
| `CONFIRMED` | RECEIVER xác nhận nhận hàng — đã cộng tồn 2 lớp, PO cập nhật | `DRAFT` |
| `APPROVED` | MANAGER duyệt — bước audit, không đụng tồn | `CONFIRMED` |

Không có đường lùi trạng thái. Sai sau `DRAFT` thì tạo GRN mới (đã ngoài phạm vi sửa/xóa item).

## Schema

### `GoodsReceiptNoteItem` (sub-document, `_id: false`, không audit riêng)

| Field | Type | Ghi chú |
|---|---|---|
| `itemId` | ObjectId | `WarehouseItem._id`, phải có trong `PO.items` |
| `sku` | string | denormalized từ `WarehouseItem.sku` |
| `expectedQty` | number | copy từ PO item tại thời điểm tạo GRN (hiển thị, không dùng để tính lại) |
| `actualQty` | number | số thực nhận, theo `unit` khai báo (có thể là alt unit) |
| `unit` | string | đơn vị nhận — quy đổi base unit khi cộng tồn |
| `lotNumber` | string? | bắt buộc nếu `WarehouseItem.isPerishable` |
| `expiryDate` | Date? | bắt buộc nếu `WarehouseItem.isPerishable` |
| `note` | string? | ghi chú lệch PO |

### `GoodsReceiptNote` (chứng từ giao dịch — `timestamps: true`, KHÔNG soft-delete, hủy bằng status)

| Field | Type | Ghi chú |
|---|---|---|
| `grnNumber` | string, unique | format `GRN-YYYYMMDD-xxxx`, sequence reset theo ngày (giống PO) |
| `purchaseOrderId` | ObjectId | → `PurchaseOrder` |
| `warehouseId` | ObjectId | copy từ PO (kho nhận hàng) |
| `status` | enum | `DRAFT` (default) `/CONFIRMED/APPROVED` |
| `items` | `GoodsReceiptNoteItem[]` | |
| `createdBy` | ObjectId | RECEIVER tạo |
| `confirmedBy` | ObjectId? | RECEIVER xác nhận (có thể khác người tạo) |
| `approvedBy` | ObjectId? | MANAGER duyệt |

Index: `{ purchaseOrderId: 1 }`, `{ status: 1 }`, unique `{ grnNumber: 1 }`.

### Thay đổi schema phụ trợ

**`Shelf`** (`apps/wms/src/warehouse/schemas/shelf.schema.ts`): thêm field denormalized

```ts
@Prop({ type: Types.ObjectId, required: true })
warehouseId!: Types.ObjectId; // denormalized từ Rack.zoneId → Zone.warehouseId — tra staging shelf nhanh, không join 3 tầng
```

Index `{ warehouseId: 1, isStaging: 1 }`. Backfill: vì `Shelf` hiện tại không có field này, cần set khi tạo Shelf mới (`WarehouseService.createShelf` phải nhận thêm `warehouseId` — resolve từ `rackId` lúc tạo, giữ nguyên input contract nếu có thể bằng cách tự tra `Rack.zoneId → Zone.warehouseId` trong service rồi lưu kết quả).

**`PurchaseOrderItem`** (`apps/wms/src/purchase-order/schemas/purchase-order.schema.ts`): thêm

```ts
@Prop({ type: Number, default: 0, min: 0 })
receivedQty!: number; // tích lũy từ mọi GRN đã CONFIRMED tham chiếu PO này (đơn vị cơ sở)
```

## API

Base path: `api/wms/goods-receipt-notes` (prefix `api/wms` từ `main.ts`).

| Method | Path | Role | Mô tả |
|---|---|---|---|
| POST | `/` | RECEIVER, ADMIN | Tạo GRN `DRAFT`, kèm items |
| POST | `/:id/confirm` | RECEIVER, ADMIN | `DRAFT → CONFIRMED`: cộng tồn 2 lớp, cập nhật PO |
| POST | `/:id/approve` | MANAGER, ADMIN | `CONFIRMED → APPROVED`: audit only |
| GET | `/` | RECEIVER, MANAGER, ADMIN | List, filter theo `status`/`purchaseOrderId`, phân trang |
| GET | `/:id` | RECEIVER, MANAGER, ADMIN | Chi tiết |

### Validate khi tạo (`POST /`)

- `purchaseOrderId` tồn tại, PO status không phải `CANCELLED`/`COMPLETED` (`PO_NOT_RECEIVABLE` nếu vi phạm).
- Mọi `itemId` trong `items[]` phải có mặt trong `PO.items[].itemId` (`GRN_ITEM_NOT_IN_PO` nếu không).
- Item có `WarehouseItem.isPerishable = true` → bắt buộc `lotNumber` + `expiryDate` (`GRN_LOT_INFO_MISSING` nếu thiếu).
- `warehouseId` copy từ PO, không cho client tự truyền.

### Validate khi confirm (`POST /:id/confirm`)

- GRN status phải là `DRAFT` (`GRN_INVALID_STATUS_TRANSITION` nếu không).
- Trước khi mở transaction: với mỗi GRN item, tính `baseQty = actualQty × factor(unit)`. Nếu GRN có nhiều dòng cùng `itemId`, **gộp `baseQty` theo `itemId` trước khi so sánh** (một PO item có thể bị nhận nhiều lô trong cùng 1 GRN). Kiểm tra `PO.items[itemId].receivedQty + Σ baseQty(itemId) ≤ PO.items[itemId].expectedQty` cho **mọi** `itemId` — vượt bất kỳ dòng nào thì chặn toàn bộ (`GRN_QTY_EXCEEDS_PO`), không cộng tồn, không đổi gì.
- Tìm staging shelf của `warehouseId` (`Shelf.findOne({ warehouseId, isStaging: true, deletedAt: null })`) — không có thì `GRN_STAGING_SHELF_NOT_FOUND`.

### Xử lý khi confirm thành công (trong `StockTransactionHelper.withStockTransaction`)

Với mỗi GRN item:

1. Nếu `isPerishable`: `findActiveLotByNumber(itemId, lotNumber)` → có thì dùng `lotId` đó, không thì `createLot({ itemId, lotNumber, expiryDate, receivedDate: now })`.
2. `stockRepo.upsertBalance(itemId, warehouseId, +baseQty, 0, 0, session)` — lớp 1.
3. `stockRepo.upsertInventory(itemId, warehouseId, stagingShelfId, lotId ?? null, +baseQty, session)` — lớp 2.
4. `stockRepo.insertMovement({ itemId, warehouseId, shelfId: stagingShelfId, lotId, type: MovementType.RECEIVE, quantity: +baseQty, refType: 'grn', refId: grn._id, createdBy: actorId }, session)` — ghi theo **từng dòng GRN item** (giữ vết lô/shelf riêng), không gộp.
5. `purchaseOrderService.applyReceivedQty(purchaseOrderId, itemId, +baseQty, session)` — gọi theo từng dòng GRN item (không gộp); method tự `$inc` nên nhiều lời gọi cùng `itemId` cộng dồn đúng. Sau khi cộng hết, tính lại status PO (đủ mọi item ≥ expectedQty → `COMPLETED`; còn thiếu ít nhất 1 item → `PARTIALLY_RECEIVED`).

Sau khi cộng hết mọi item: cập nhật `GRN.status = CONFIRMED`, `confirmedBy = actorId` (cùng session).

**Sau khi transaction commit** (ngoài transaction — BullMQ không tham gia Mongo transaction): với mỗi item, `stockService.publishAvailableForItem(itemId, +baseQty)`.

### Xử lý khi approve (`POST /:id/approve`)

- GRN status phải là `CONFIRMED` (`GRN_INVALID_STATUS_TRANSITION` nếu không).
- Chỉ đổi `status = APPROVED`, `approvedBy = actorId`. Không đụng tồn kho, không transaction Mongo cần thiết (single-document update).

## Error codes mới (`libs/common/src/errors/error-codes.ts`, nhóm `WMS — Goods Receipt Note`)

| Code | Status | Message |
|---|---|---|
| `GRN_NOT_FOUND` | 404 | Không tìm thấy phiếu nhập kho |
| `GRN_INVALID_STATUS_TRANSITION` | 409 | Trạng thái phiếu nhập kho không hợp lệ cho thao tác này |
| `GRN_ITEM_NOT_IN_PO` | 400 | Mặt hàng không thuộc đơn đặt hàng tham chiếu |
| `GRN_LOT_INFO_MISSING` | 400 | Mặt hàng có hạn dùng — cần nhập lô và hạn sử dụng |
| `GRN_QTY_EXCEEDS_PO` | 400 | Số lượng nhận vượt quá số lượng đặt còn lại của đơn hàng |
| `GRN_STAGING_SHELF_NOT_FOUND` | 404 | Kho chưa cấu hình vị trí nhận hàng (staging) |
| `PO_NOT_RECEIVABLE` | 409 | Đơn đặt hàng đã hủy hoặc đã nhận đủ, không thể tạo phiếu nhập mới |

## Thay đổi phụ trợ cần làm ở module khác

- **`PurchaseOrderModule`**: thêm `exports: [PurchaseOrderService]` (hiện chưa export).
- **`PurchaseOrderService`**: thêm method
  ```ts
  applyReceivedQty(poId: string, itemId: string, deltaBaseQty: number, session: ClientSession): Promise<void>
  ```
  cộng dồn `receivedQty` cho đúng item trong `PO.items`, tính lại `status` (giữ nguyên nếu đang `CANCELLED`— không nên xảy ra vì đã chặn ở `PO_NOT_RECEIVABLE`), lưu qua session truyền vào (cùng transaction GRN).
- **`WarehouseService`/`WarehouseRepository`**: thêm method tìm staging shelf theo `warehouseId`; `createShelf` cần tự resolve và lưu `warehouseId` denormalized (tra `Rack.zoneId → Zone.warehouseId`).
- **`GoodsReceiptNoteModule`** import: `PurchaseOrderModule`, `StockModule`, `WarehouseModule`, `MongooseModule.forFeature([GoodsReceiptNote])`.
- Wire `GoodsReceiptNoteModule` vào `AppModule`, ngay sau `PurchaseOrderModule`.

## DTO conventions (theo `dto-conventions.md`)

- `CreateGoodsReceiptNoteDto` (request): `purchaseOrderId` (`@IsMongoId`), `items: CreateGoodsReceiptNoteItemDto[]` (`@ValidateNested({ each: true }) @Type(...)`).
- `CreateGoodsReceiptNoteItemDto`: `itemId`, `sku`, `actualQty` (`@Min(0)`), `unit`, `lotNumber?`, `expiryDate?` (`@IsISO8601` hoặc string), `note?`.
- `GoodsReceiptNoteResponseDto` / `GoodsReceiptNoteItemResponseDto`: `@Expose()` toàn field cần, `_id → id` qua `@Transform`, `status` có `enum: GoodsReceiptNoteStatus` trong `@ApiProperty`.
- Mọi `@Roles(...)` ghi `— [ROLE1, ROLE2]` vào `@ApiOperation summary`.
