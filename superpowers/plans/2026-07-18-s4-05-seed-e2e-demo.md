# S4-05: Seed data + E2E happy-path WMS + bug bash + demo — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship a repeatable seed script + one E2E happy-path test that proves the WMS core flow (login → PO → GRN confirm → put-away → goods-issue → stock-count) holds the two-layer stock invariant end-to-end, plus a demo script for presenting it and a written bug-bash review of the modules involved.

**Architecture:** Seed script boots a Nest **application context** (no HTTP) and calls the real `AuthService`/`WarehouseService`/`StockService`/`SupplierService` methods so hashing/validation logic isn't duplicated. The E2E spec boots the full `AppModule` via `Test.createTestingModule` + `supertest`, drives every step through real HTTP routes (auth, guards, validation pipe, response envelope all exercised for real), except the goods-issue trigger — which has no HTTP endpoint and is only reachable by enqueuing `order.ready_to_fulfill` onto the real `QUEUES.ORDER` BullMQ queue, then polling `GoodsIssueRepository.findByOrderId` until the consumer has processed it. Stock invariants are asserted by reading `StockBalance`/`InventoryStock`/`StockMovement` Mongoose models directly via `getModelToken()` — acceptable here because these are test-oracle reads asserting an invariant, not application business logic reading across app boundaries.

**Tech Stack:** NestJS (monorepo `apps/wms`), Mongoose (`@nestjs/mongoose`), BullMQ (`@nestjs/bullmq`), Jest + `ts-jest` + `supertest`, `ts-node` for the standalone seed script.

## Global Constraints

- **No Docker/Redis in the plan author's environment** — every task below is written and statically reviewed but **not executed** by the plan author. The user runs `pnpm seed:wms` and `pnpm test:e2e` themselves after starting infra (`docker compose -f docker-compose.local.yml up -d redis`, Atlas already configured in `.env`) and reports back if something fails.
- Global HTTP prefix is `/api/wms` (`apps/wms/src/main.ts`) — every route in this plan must be called with that prefix.
- Comments in Vietnamese explaining *why*, matching existing codebase style (per project `CLAUDE.md`).
- No `any` anywhere (project ESLint rule `@typescript-eslint/no-explicit-any` — build fails on violation).
- Services in this codebase throw `AppException('CODE')`, never raw NestJS exceptions — this applies to any service code touched, not to test/script code calling HTTP (which just asserts status codes).
- `PurchaseOrderStatus` defaults to `CONFIRMED` at creation — there is no separate "confirm PO" endpoint. Do not invent one.
- `ConfirmPutAwayLineDto` / `ConfirmGoodsIssueLineDto` key off `itemBarcode` + `shelfCode`, not `itemId` — the seeded `WarehouseItem` must have a `barcode` set.
- `CreateStockCountDto` auto-generates item lines from current inventory; `StockCountResponseDto.items[].systemQty` is the authoritative "current system quantity" to echo back as `actualQty` for a zero-delta happy path — don't separately track expected quantities in the test.
- Idempotency in the seed script is **check-then-create** (query by unique field first), not catch-duplicate-key — `AuthService.createUser`/`userRepo.create` do not map Mongo `E11000` to a clean `AppException`, so relying on a caught duplicate-key error would leak a raw Mongo error through code that should never see it.

import { AuthService } from '../auth/auth.service';
import { UserRepository } from '../auth/repositories/user.repository';

/**
 * Seed data cho demo/E2E: admin + 5 role nhân viên, 1 kho + zone/rack/shelf,
 * vài WarehouseItem, 1 supplier + bảng giá. Idempotent — chạy lại không tạo trùng
 * (check-then-create, KHÔNG bắt lỗi duplicate-key vì AuthService không map

export async function seed(): Promise<void> {
  const app = await NestFactory.createApplicationContext(AppModule);
  try {
    await seedUsers(app);
    logger.log('Seed hoàn tất.');
  } finally {
    await app.close();
  }
}

const SEED_PASSWORD = 'Seed@12345';

const SEED_USERS: { username: string; role: WmsRole; name: string }[] = [
  { username: 'seed_manager', role: WmsRole.MANAGER, name: 'Seed Manager' },
  { username: 'seed_receiver', role: WmsRole.RECEIVER, name: 'Seed Receiver' },
  { username: 'seed_picker', role: WmsRole.PICKER, name: 'Seed Picker' },
  { username: 'seed_printer', role: WmsRole.PRINTER, name: 'Seed Printer' },
  { username: 'seed_counter', role: WmsRole.COUNTER, name: 'Seed Counter' },
];

async function seedUsers(
  app: Awaited<ReturnType<typeof NestFactory.createApplicationContext>>,
): Promise<{ adminId: string }> {
  const authService = app.get(AuthService);
  const userRepo = app.get(UserRepository);

  let admin = await userRepo.findByUsername('seed_admin');
  if (!admin) {
    const dto: CreateUserDto = {
      username: 'seed_admin',
      password: SEED_PASSWORD,
      name: 'Seed Admin',
    };
    const created = await authService.bootstrapAdmin(dto);
    admin = await userRepo.findByUsername('seed_admin');
    logger.log(`Tạo admin: seed_admin / ${SEED_PASSWORD}`);
    void created;
  } else {
    logger.log('admin đã tồn tại — bỏ qua.');
  }
  if (!admin) {
    throw new Error('Không thể tạo hoặc tìm thấy seed_admin sau bootstrap.');
  }
  const adminId = admin._id.toString();

  for (const u of SEED_USERS) {
    const existing = await userRepo.findByUsername(u.username);
    if (existing) {
      logger.log(`${u.username} đã tồn tại — bỏ qua.`);
      continue;
    }
    const dto: CreateUserDto = {
      username: u.username,
      password: SEED_PASSWORD,
      name: u.name,
      roles: [u.role],
    };
    await authService.createUser(dto, adminId);
    logger.log(`Tạo ${u.username} (${u.role}) / ${SEED_PASSWORD}`);
  }

  return { adminId };
}

if (require.main === module) {
  seed().catch((err: unknown) => {
    logger.error('Seed thất bại:', err);
    process.exit(1);
  });
}

**Idempotency for this task's entities (confirmed by reading each service, not assumed):**
- `WarehouseService.createWarehouse` has **no duplicate guard at all** — `Warehouse` has no unique `code`/`sku` field, only `name`+`address`, and the service comment explicitly says it skips a code-conflict check (`// Warehouse chỉ có name + address, không có code → bỏ qua kiểm tra WAREHOUSE_CODE_EXISTS`). Re-running the seed script **will** create a second "Kho trung tâm (seed)" warehouse with a new id. Guard this explicitly in the seed script: before calling `createWarehouse`, list warehouses via `warehouseService.listWarehouses()` and find one whose `name === 'Kho trung tâm (seed)'`; if found, reuse its id and skip creating zone/rack/shelf/items/supplier under it too (assume they were already seeded alongside it in a prior run — this is a reasonable assumption for a single seed script that always creates its full tree together, but note it explicitly in a code comment so a future reader isn't surprised).
- `StockService.createWarehouseItem` **does** pre-check `sku` and throws `AppException('STOCK_ITEM_SKU_CONFLICT')` cleanly (confirmed: `const existing = await this.stockRepo.findItemBySku(data.sku); if (existing) throw new AppException('STOCK_ITEM_SKU_CONFLICT');`). Wrap each `createWarehouseItem` call in a try/catch that catches specifically that code and looks up the existing item instead (via `stockService`'s underlying repository, or re-derive by reusing the warehouse-reuse branch above — since items are re-seeded together with the warehouse, the warehouse-exists check already covers this in practice, but keep the try/catch as a defensive second layer since item creation could theoretically be retried independently of warehouse creation if this script is ever refactored).
- `SupplierService.createSupplier` — read `apps/wms/src/supplier/supplier.service.ts`'s `createSupplier` method during Step 1 (not yet confirmed) to determine whether it pre-checks `code` the same way `createWarehouseItem` does. Apply the same pattern (try/catch on the specific `AppException` code if one exists) or an explicit pre-check query if it doesn't.
- Given the warehouse-reuse branch above already prevents re-running the whole tree, the simplest correct implementation is: **check for the named warehouse first: if it exists, log "seed data đã tồn tại — bỏ qua toàn bộ warehouse/item/supplier" and return early from `seedWarehouseAndItems` without calling any create methods.** This avoids needing separate duplicate handling for zone/rack/shelf/item/supplier individually, since they're never reached on a second run. Implement it this way rather than adding try/catch to every single create call.

   * tổng quantity của mọi InventoryStock (lớp 2, chi tiết theo shelf/lot)

### Task 6: Bug bash — code review of happy-path modules

**Files:** none created/modified by this task itself — it produces a written report, not a diff. If findings surface actual bugs worth fixing, each fix becomes its own follow-up commit using the normal edit/test/commit cycle, not bundled into this task.

**Interfaces:** none — this is a review task.

- [ ] **Step 1: Review `apps/wms/src/put-away-suggestion/put-away-suggestion.service.ts` for logic bugs**

Focus: the 3D volume matching (`fits()`, `rankSingleShelf()`, `combineShelves()`) already read in full during design (see design doc). Check specifically: does `fits()` correctly reject an item where any single dimension exceeds the shelf's largest dimension even after sorting both descending (the current sort-and-compare-by-index approach is a known-correct heuristic for "does it fit in some rotation" but verify it doesn't false-positive when shelf dims include a zero/undefined coerced to `0` via `?? 0` — an all-zero shelf with no dimensions declared would pass `fits()` trivially since `itemDims.every(d => d <= 0)` is only true if item dims are also 0, so likely safe, but confirm by tracing one concrete example with real numbers).

- [ ] **Step 2: Review `apps/wms/src/goods-receipt-note/goods-receipt-note.service.ts` confirm method for transaction correctness**

Already confirmed during plan authoring: the method wraps its stock writes in `this.stockTransactionHelper.withStockTransaction(async (session) => { ... })` (line ~158), so the 2-layer update is atomic — no separate transaction-safety finding needed here. Instead, read the full body of the callback and check: does every write inside it correctly pass `session` through to each repository call (`upsertBalance`, `upsertInventory`, `insertMovement`, PO status update)? A write that forgets to pass `session` silently escapes the transaction (Mongoose does not error on this — it just writes outside the transaction), which is a real, easy-to-miss bug class in transactional code. Flag any repository call inside the `withStockTransaction` callback that doesn't receive `session` as an argument.

- [ ] **Step 3: Review `apps/wms/src/put-away/put-away.service.ts` confirm-line method**

Same confirmed pattern: `withStockTransaction` wraps the confirm-line body (line ~118). Apply the same "every write inside the callback must forward `session`" check as Step 2. Additionally check: after decrementing the staging `InventoryStock` row, does the code handle the case where `quantity` reaches exactly 0 (does it delete the row, or leave a `quantity: 0` row)? Either is defensible, but confirm the `assertTwoLayerInvariant` helper in the e2e test (Task 3) still holds either way — a `quantity: 0` row contributes `0` to the sum either way, so this shouldn't break the invariant, but confirm no `unique` index violation occurs on the next put-away to the same staging shelf if the row is left at 0 rather than deleted.

- [ ] **Step 4: Review `apps/wms/src/goods-issue/order-ready.consumer.ts` and `goods-issue.service.ts` for BullMQ retry idempotency**

Focus: already confirmed `createFromOrderReady` checks `findByOrderId` first and returns early if a `GoodsIssue` already exists for that `orderId` — this is idempotent against full-job retries. Check whether a **partial failure** (e.g. it creates the `GoodsIssue` doc but throws before returning, due to an error in one line's `stockRepo.findItemBySku` lookup for a later item) could leave a partially-created `GoodsIssue` that then blocks all future retries from ever completing the missing lines (since the early-return-on-existing check has no way to "resume" a partial doc). Flag this if found — it's a real gap given BullMQ retries the whole job on any throw.
